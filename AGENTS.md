# Робота з Люменом

- Публікувати зміни до приватного `alex-hohaizel/lumen-family-agent` звичайним Git: перевірений checkout, commit, один `git push`. Доступ GitHub-плагіна не означає авторизацію Git CLI. Перевіряти це на початку роботи.
- Якщо CLI потребує входу, використати підтримуваний вхід GitHub CLI. Не замінювати відсутній доступ сотнями викликів завантаження файлів. Не обходити відмови автоматичної перевірки.
- У Git тримати код, конфігурацію, залежності, потрібні тести й fixtures, готові ресурси та стислу документацію. PNG-прев’ю лишаються еталонами розробки. Не комітити робочі рендери, пробні відео, звіти виконання тестів, кадри, джерельні атласи або `sticker-lab`.
- `npm run build` створює тільки production `dist/src`; `npm run build:test` — `.test-build`. `npm run build:release` створює окремий `.release` за allowlist із production-залежностями. Не додавати до нього тести, docs/tools, PNG-прев’ю або авторську історію; не чистити сторонні каталоги чи symlink-залежності.
- Потрібні джерела й рецепти зберігати окремим архівом матеріалів проєкту. Пам’ять чату містить рішення та посилання; вона не замінює файли. Перед вилученням потрібних джерел із Git зберегти й перевірити архів.
- Передавати WEBM, PNG і manifest звичайними файлами. Не дробити їх на частини й не вводити збирання транспортних частин у `pretest`.
- Перевірки готового набору, хешів, порядку й доставки залишати в основних тестах. Перевірки виробничих джерел виконувати окремо з авторським архівом. Результати тестів писати в тимчасові каталоги з очищенням.
- Для виправлення наліпок не перебудовувати поведінку бота й не генерувати заново вже прийняті файли без конкретного дефекту. Зберігати всі 120 ID, емоцій, сцен і погоджений порядок.
- Продовження релізу починати з HEAD GitHub і стану чинного Render. Не повторювати завершені етапи без нової причини. Вести один короткий запис стану замість копій журналів у коді.
- Один повний обов’язковий GitHub `verify` має пройти для точного SHA; він включає функціональні тести й перевірку runtime-пакета. Render — `After CI Checks Pass`, build `npm ci --include=dev && npm run build:release && node tools/release/finalize-render.mjs`, start `cd .release && npm start`. Звіряти фактичні налаштування, не лише `render.yaml`. Не дублювати повний набір на Render і не запускати другий ручний deploy після автоматичного. Для ручного deploy явно перевірити CI цього SHA.
- Широку живу діагностику вмикати лише явно через `npm run diagnostics` / `--diagnostics` у єдиному worker з чинними lease та Auth. Звичайний запуск залишає її `not_run`; не запускати для asset-only випуску. Ручні інструменти — у `tools/diagnostics`, результати — поза кодом, тимчасові каталоги — з очищенням.
- Не змінювати приватність репозиторію, модель GPT-6.1-Sol, конфігурацію голосу, існуючі секрети, дані чатів або ресурси Render без окремого доручення.
