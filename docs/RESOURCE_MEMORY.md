# Пам’ять worker і важка робота

Один worker володіє Telegram poller/Auth lease. Збільшення кількості інстанцій не є способом виправлення піків пам’яті без зміни цієї архітектури. Тариф, модель, голос, secrets і дані ця зміна не змінює.

## Вимірювання

`runtime_memory` пишеться при старті sampler, кожні 30 секунд, перед/після важкої операції та при поміченому тиску на RAM. Джерело `cgroup_v2` / `cgroup_v1` враховує контейнер разом із дочірніми процесами; відомі обмеження предків перевіряються разом із їхнім usage. Вибір ефективного предка використовує той самий90% admission margin, що й worker; менший raw headroom не підміняє цю політику. Окремі поля Node: RSS, heap, external і arrayBuffers. ArrayBuffers уже входить до external — їх не додавати.

Якщо cgroup недоступний, `source=node_process_only`, `limit_bytes=null`: це лише пам’ять Node, не всі процеси. Unlimited також має `null`, а не вигадані 512 MiB. В такому випадку залишається серіалізація, але перевірка запасу за невідомим лімітом не блокує роботу (`admission=limit_unknown`). Це обмеження захисту, а не доказ достатньої RAM. На Linux кількість дочірніх процесів вимірюється обмеженим обходом `/proc`; неможливість повного підрахунку дає `null`.

Події містять тільки числові показники, timestamp, фазу та тип операції з фіксованого переліку. Немає текстів, URL, назв документів, tool arguments/results, chat/user/task/source IDs або командного рядка процесів. `scheduled_dispatch` містить лише кількість reminder/task, максимальне запізнення й тривалість committed dispatch. `background_task_step` — фазу й номер кроку. Відмова logger не змінює результат операції.

## Admission і відновлення

Альтернативи: лише вимірювання не запобігає новому OOM; окремий сервіс або більший тариф виходять за межі цієї зміни. Обрано вимірювання + обмежена черга + перевірка запасу перед callback існуючого єдиного heavy slot.

За відомого ліміту `current + reserve <= 0.9 * limit`: reserve 192 MiB для браузера/PDF/DOCX preview, 128 MiB для інших операцій. При нестачі — одна безпечна спроба закрити браузер без сесій і без активної операції, повторне вимірювання, потім чесна відмова `worker_memory_busy`. Немає нескінченного очікування RAM. Черга heavy slot — до 8 очікувачів, очікування до 30 секунд; черга браузера — до 4 разом з активною операцією. Скасування перевіряється також після вимірювань, до callback.

Це консервативна початкова політика, **не жорсткий ліміт алокацій** і не гарантія від усіх OOM. Зростання всередині callback та буфери, завантажені caller до admission, усе ще можливі. Логи `observed_peak_bytes` є вибірковими вимірюваннями; дуже короткі піки можуть бути пропущені.

Після закриття останнього browser context процес закривається одразу. Idle timeout — 60 секунд; його cleanup серіалізований із browser operations і не закриває активну навігацію/PDF. Pressure cleanup не руйнує живі сесії заради іншої операції.

Task із ресурсною відмовою, включно з переповненням браузерної черги browser_busy, зберігається як `needs_input`, без автоматичного наступного model-step. Уже claimed external effect залишається `uncertain`; ресурсна помилка не дозволяє сліпий повтор. Media render зберігає існуючий `repair` і матеріали. Візуальне декодування повертає вкладення у pending без витрати decode-attempt і має 30-секундну паузу перед наступною спробою. Forget/cancel/revision fences залишаються чинними.

## Нічний розклад і локальні перевірки

`mode=reminder` ставить готовий текст у чергу, не запускаючи planner/browser/PDF. `mode=task` створює агентне доручення, яке може використовувати інструменти. Доставка нагадування або холодне відновлення runtime можуть окремо викликати текстову модель для локалізації/налаштувань. Час 04:00 сам по собі не доводить причину OOM; потрібна часова прив’язка dispatch, heavy work і RAM без читання вмісту чатів.

Після `npm run build` та `npm run build:test` нові resource/browser/scheduling/recovery тести виконуються з `.test-build/test`. Повний локальний regression — `npm test`; релізний CI gate — `npm run verify` на точному SHA.

`python3 tools/diagnostics/resource-pilot.py` запускає тільки синтетичні DOCX→PDF, image decode та FFmpeg у власному локальному дереві процесів. Для macOS можна явно передати `LUMEN_CHROMIUM_PATH` до встановленого Chrome; це не змінює production. Результат — сумарний sampled RSS процесів із можливим подвійним обліком shared pages, а не cgroup usage. `memory_limit_enforced=false`: таке вимірювання не сертифікує Render 512 MiB. Звіти — лише поза репозиторієм; тимчасові матеріали очищуються. Production probes, другий worker і `--diagnostics` для цього не потрібні.

Випуск/відкат — за `AGENTS.md` і `docs/RELEASING.md`; ця локальна перевірка сама не публікує код і не змінює Render.
