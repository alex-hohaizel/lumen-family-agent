# Випуск Люмена

Код і перевірки зберігаються у приватному GitHub. Джерела анімації та журнали — у [авторському архіві](https://chatgpt.com/library?file_id=libfile_eacd327e079c8191ac88bc43375e458a&account_id=personal). Старий manifest з історією й невикористані ресурси збережено в [архіві очищення](https://chatgpt.com/library?file_id=libfile_5cb705ea45848191b89cdef4e5bce93e&account_id=personal).

1. Почати з актуальних GitHub HEAD, стану чинного Render і короткого запису доставки. Не відновлювати завершений реліз із застарілого звіту. Звірити `git ls-remote origin HEAD`, робоче дерево та відсутність іншого активного деплою.
2. Узгодити версію в `package.json`, `package-lock.json`, `src/release.ts` і `CHANGELOG.md`. Для службового виправлення залишити незмінені ресурси. Не генерувати повторно прийняті анімації.
3. Для зміни стікерів переносити лише погоджені готові WEBM/PNG й manifest. Зберігати всі 120 ID/емоцій/сцен/порядок, перевірити хеші й оновити approved fingerprint та еталон лише за реально погодженої зміни. PNG потрібні CI, не runtime-пакету.
4. Локально виконати адресні перевірки змінених шляхів. Переглянути diff і список файлів: жодних секретів, runtime, архівів, пробних відео, кадрів чи звітів виконання. Закомітити і передати всі зміни звичайним `git push`. Не використовувати завантаження сотнями API-викликів або transport chunks.
5. Обов’язковий GitHub job `verify` виконує `npm run verify`: повний функціональний набір, тести пакування, побудову `.release`, інвентаризацію/хеші/залежності й локальну перевірку медіа з цього пакета. Помилка завершує gate; зелений результат потрібний саме для SHA, який буде розгорнуто. Перевірки Docker виконуються після змін відповідного способу розгортання.
6. Цільові налаштування чинного worker `srv-dbfl0je7bikc73dvg0qg`: Auto-Deploy **After CI Checks Pass**, build `npm ci --include=dev && npm run build:release && node tools/release/finalize-render.mjs`, start `cd .release && npm start`. Render збирає перевірений коміт без другого повного `npm test`. Зміна `render.yaml` сама по собі не змінює наявний сервіс із вимкненим Blueprint Sync: звірити фактичний API/Dashboard. Якщо цільові налаштування ще не застосовані, міграцію не вважати завершеною.
7. Після push не запускати другий ручний deploy, якщо Render уже запускає автоматичний. Відстежувати один deploy ID та його commit. Для ручного випуску або відновлення спочатку перевірити успішний `verify` потрібного SHA. Ручний deploy є окремою операцією й не отримує CI-gate автоматично.
8. Підтвердити Live потрібного SHA, версію, `sticker_pack_verified` для 120 позицій, `sticker_pack_ready`, потім `lumen_started`. Обов’язкові DB/config/lease/Telegram-перевірки залишаються перед стартом чатів. Публікація стікерів відновлюється з наявного checkpoint.
9. Зберегти один короткий зовнішній запис: SHA, CI/deploy ID, результат перевірки пакета, Telegram і запуск. Не комітити журнали виконання. Не повторювати пройдені етапи без зміни чи нового дефекту.

## Межі пакета

`.release` містить скомпільований код, production dependency closure, основну SQL-схему, шрифт/ліцензію, потрібні ресурси майстра/профілю/повідомлень, 120 WEBM і runtime manifest. Список включених файлів і хешів записується в `release-manifest.json`. Вихідні тести, `.test-build`, документація, діагностичні інструменти, PNG-прев’ю та авторська історія не входять. Наприкінці native Render build захищений finalizer повторно перевіряє автономність `.release`, точний SHA та production-залежності й прибирає лише визначені build/checkout матеріали, включно з вихідними тестами, PNG та кореневою копією node_modules. Дані runtime/backups, зовнішній RUNTIME_DIR і Git-метадані зберігаються. Finalizer дозволений лише для штатного Render build-root; локально його не запускати. Процес працює з `.release`.

Широка жива діагностика тепер явна: `npm run diagnostics` запускає звичайний worker із `--diagnostics`, тією самою lease та Auth. Потрібний контрольований перезапуск єдиного екземпляра. Не запускати паралельний процес або другий OAuth refresh manager. Для звичайного asset patch не виконувати model/web/browser probes повторно.

## Відкат

Зберегти поточний deploy ID/SHA до випуску. Build failure не змінює старий worker; persistent disk передбачає перерву під час заміни instance. Не прирівнювати provider rollback до відкату даних. Для відкату до старого коміту до 1.13.2 повернути його build `npm ci --include=dev && npm test && npm prune --omit=dev` і start `npm start`, бо старий код не створює `.release`. Для нового коміту використати його відомий CI результат і сумісні команди. Перевірити фактичний режим Auto-Deploy, щоб автоматичний випуск не замінив обраний rollback. Базу й диск відкат коду не повертає.

Не змінювати модель, голос, секрети, дані, приватність, згоду чи платні ресурси в цьому службовому випуску.


### Сумісність1.13.3/schema21

Schema21 additive; повторне застосування й перехід із exact v20 перевіряються ізольовано. Після створення нових standalone private schedules повертати a1fd79/1.13.2 небезпечно: стара dispatch policy ігнорує їх audience і може поставити приватний текст у group outbox. Це відтворений негативний oracle, а не дозволений production експеримент.

Старий artifact придатний для rollback лише до приймання нових1.13.3 доручень і за підтвердженої відсутності нових приватних schedules/effects. Після такого ingress потрібен privacy-compatible forward fix, що зберігає audience/source/cancel/forget fences; blind rollback наa1fd79 заборонений. За аварії зупинити залежний dispatch, reconcile claimed/uncertain effects і відновити сумісний код. Не стирати jobs/дані для підгонки сумісності й не відновлювати старий snapshot поверх пізнішого forget. Backup source/активів і попередній deploy ID не означають готового rollback усієї БД.

Поточний CI додатково запускає bounded standalone DOCX/PDF/PNG smoke під Linux cgroup512MiB без swap і0.5CPU, з перевіркою реальних limit/quota/peak/OOM. Це перевірка конкретного package, не атестація всіх можливих production навантажень. Тариф, інстанції й ресурси Render не змінюються.

### Сумісність1.13.4 і pending погоджень

Нової міграції немає: схема21 і privacy epochs збережені. Перед новим r2 ingress попередній26112af/1.13.3 є сумісним за схемою й audience, але повертає дефект скасування. Після створення нових reminder_cancel proposals/vote receipts старий interaction runtime не розуміє їхнього launch та перевірки голосів. Тому schema compatibility не означає безпечного сліпого replay старим кодом: потрібен сумісний forward fix або окрема перевірена процедура зупинки/ізоляції таких pending operations. Не стирати картки, jobs чи дані для підгонки rollback.

### Schema22: діагностичні інциденти

1.13.6 додає `diagnostic_incidents` і metadata кодів до чинних результатів без переписування існуючих jobs, прав чи активів. Код21 може прочитати більшість старих доменних рядків, але це не доводить privacy-compatible rollback: він не має нових pause/erase/TTL hooks для source-less інцидентів. Після появи schema22 інцидентів використовувати сумісний forward fix або окремо перевірений rollback, що зберігає їхній lifecycle; не відновлювати стерті дані зі старого архіву. Source archive не є backup чинної БД чи секретів.
